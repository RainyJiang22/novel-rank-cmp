# 小说热榜 — 功能分析

## 概述

新建独立 Kotlin Compose Multiplatform 项目「小说热榜」，目标是在 Android、iOS、桌面端查询起点、番茄、七猫、晋江的分类前十作品。首版工程位于独立 `novel-rank-cmp` 仓库，三端和四站范围已经确定。

已确认：按网站、类型查询前十热榜。实现假设：第一版用共享 CMP UI + Python 聚合服务，提供来源跳转、榜单口径、采集时间、刷新、关键词筛选、服务地址配置。各站分类和热度单位保持原样，不做跨站合并排名。网站没有相应分类榜时不把全站榜过滤结果伪装成分类前十。

本次交付阶段（2026-11-03 用户最新指令）：**实现 server v0.1.0**。三端骨架已经初始化，本轮实现四站目录、排名适配、状态与缓存、API 和测试文档。客户端交互链仍为规划，不在本轮接入；不进行原生构建或公网部署。项目远程为 `https://github.com/RainyJiang22/novel-rank-cmp.git`。

工作流：`quality_gate=off`，来源为技能默认值及用户既有偏好；本轮保留普通测试与 API 链路；最终质量验收为 `SKIPPED`。

## 一、交互链

### 场景 1：查询分类前十

**用户故事**：作为小说读者或选题者，我想选择网站和类型，查看该类型前十作品及真实来源。

打开应用 → 加载网站目录 → 选择网站 → 选择该站榜单与分类 → 查看排名、书名、作者、热度原始单位 → 点击作品在系统浏览器打开来源。桌面宽屏展示网站侧栏，手机展示横向网站选项。

### 场景 2：刷新和失败重试

**用户故事**：作为用户，我想知道榜单是否新鲜，并在来源暂不可用时看到原因。

点击刷新 → 显示加载进度 → 展示采集时间与缓存标记；若访问受限、页面变化或超时，展示具体状态与来源入口；若存在旧快照，明确标记过期并保留原采集时间。

### 场景 3：连接自己的服务

打开服务设置 → 输入 HTTP(S) 聚合服务地址 → 保存 → 重新加载目录。默认桌面/iOS 模拟器使用 localhost，Android 模拟器使用 10.0.2.2；真机输入同网段服务地址。

## 二、逻辑树

### 事件流

| 时刻 | 事件 | 处理 | 新事件 |
| --- | --- | --- | --- |
| T1 | 客户端进入首页 | GET /api/v1/catalog | 网站、分类、榜单目录加载完成 |
| T2 | 更换网站、分类、榜单 | 取消前一请求，验证组合，查询 top10 | 加载、成功或失败 |
| T3 | 服务收到合法请求 | 使用来源适配器与按完整查询键缓存 | 原始来源顺序前十 |
| T4 | 点击刷新 | 绕过新鲜缓存，遵守来源请求间隔 | 最新结果或显式旧快照 |
| T5 | 点击作品 | 校验 HTTP(S) 链接并打开浏览器 | 原站作品页 |

### 状态流转

| 实体 | 触发 | 前状态 | 后状态 |
| --- | --- | --- | --- |
| 客户端页面 | 查询 | 任意 | Loading → Ready / Error |
| 服务榜单 | 来源响应 | 未知 | ok / partial / blocked / unavailable / parse_error |
| 缓存快照 | 刷新失败 | 已存在快照 | stale，采集时间不变 |

### 异常流与回退

| 异常 | 条件 | 用户反馈 | 回退 |
| --- | --- | --- | --- |
| 目录请求失败 | 服务断开或地址错误 | 连接失败、设置地址、重试 | 不填充假数据 |
| 来源访问受限 | 验证页面、202/403/429 | 来源受限 | 原站链接、有限期旧快照 |
| 解析失效 | 预期容器或分类不匹配 | 页面结构变化 | 不返回成功空榜 |
| 作品不足十条 | 来源真实返回少于十条 | 已获取 N/10 | 保留原名次，不补齐 |
| 元数据乱码/部分失败 | 书名为私有区字符等 | 部分数据可用 | 保留来源位置并说明字段缺失 |
| 快速切换 | 旧请求晚返回 | 保持当前筛选结果 | 取消旧请求并校验请求身份 |

## 四、结论

先固定目录与接口契约，再建立四站独立适配器和测试，再实现三端共享 UI，最后执行 API 链路并推送独立 GitHub 仓库。复杂度集中在站点结构变化、乱码、分类与榜单口径匹配。暂不实现章节抓取、登录付费内容、验证码处理、跨站统一热度、账号体系、后台持续扫榜和历史趋势。
